Object lifetime

C reaches a Brython object through a handle, a number the bridge maps to the object. The bridge reclaims handles by three mechanisms:

  • tp_dealloc, for the references C owns (a new object, a Py_INCREF): they outlive the C call, so the bridge counts them in its refcount table; when a count reaches 0, it calls the type's tp_dealloc, which frees the C instance. The test creates an object in C and drops it there, never showing it to Python, once per call.
  • Handle scopes, for the references C only borrows during a call (its arguments, the items it reads): every handle made during the call is released when the call returns, as a borrowed reference in CPython. The test's C function walks a small graph, 91 temporary handles per call.
  • The collection, for the objects Python has held: the wrapper keeps the reference C gave it, so dropping the object leaves its count at 1 and runs no tp_dealloc. A collection of the whole heap, which BryTorch's page runs between two tests, proves the object unreachable and frees it. The test creates an object from Python and drops it, once per call, with a collection every 200 calls.

tests/lifetime.py makes 2000 calls with each mechanism switched on (A), then off (B): on, its table stays flat; off, it grows by what the mechanism reclaims.
